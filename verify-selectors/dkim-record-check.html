DKIM Record Check Guide: Verify Selectors,

    Public Keys, And DNS Records

    DomainKeys Identified Mail, commonly known as DKIM, is a core email authentication standard that helps receiving systems verify whether a message was authorized by the sending domain and whether it was altered in transit. Alongside SPF and DMARC, DKIM supports domain authentication, phishing prevention, email spoofing protection, and stronger email deliverability. To discover more, just click on the link.


    Check #1: Verify the DKIM Selector Used by Your Email Service


    The DKIM selector identifies which DKIM record should be used for DKIM validation. It appears in the DKIM signature inside the email header, usually as the s= tag. The signing domain appears as the d= tag. Together, these values tell the receiving mail server where to perform the DKIM lookup.

    For example, if an email header includes:

    DKIM-Signature: v=1; a=rsa-sha256; d=example.com; s=selector1;

    The DKIM selector is selector1, and the signing domain is example.com. The selector record is queried at:

    selector1._domainkey.example.com





    That hostname should return a DKIM record containing the public key. If the DKIM selector is incorrect, missing, expired, or not published at the correct DNS host, DKIM validation will fail even if the private key is signing messages correctly.

    Different hosted email service platforms use different selector formats. Google Workspace often uses a selector such as google, Microsoft 365 commonly uses selectors such as selector1 and selector2, and services like Zoho Mail, ProtonMail, Mailchimp, SendGrid, Mailgun, Amazon SES, Mailjet, SocketLabs, and Atmail each provide their own DKIM selector during setup. Some providers rotate selectors automatically, while others require manual DNS management.

    When checking the DKIM selector, inspect a real outbound email sent through the platform. Send a message to Gmail, Outlook, Yahoo Mail, or a testing mailbox, then open the full email header. Look for the DKIM signature and confirm:

    • The s= value matches the DKIM selector provided by your email service.

    • The d= value matches your sending domain or an authorized subdomain.

    • The correct selector record exists in DNS.

    • The DKIM signature aligns with your DMARC policy where required.

    • The message is being signed by the expected mail server, SMTP service, or email relay.


    Check #2: Validate the DKIM Public Key Format, Length, and Syntax


    A DKIM record contains the public key used in public key cryptography to verify the cryptographic signature created with the matching private key. This Key pair is the foundation of DomainKeys Identified Mail. The private key signs selected headers and body content; the public key allows receiving systems to verify message integrity without exposing the private key.

    A typical DKIM record published as a DNS TXT record looks like this:

    v=DKIM1; k=rsa; p=MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8A...

    The most important tags include:

    • v=DKIM1, which identifies the record as a DKIM record.

    • k=rsa or another supported key type, depending on the provider.

    • p=, which contains the public key.

    • Optional tags such as t=s, which can restrict signing to the exact domain.

    During a DKIM record check, validate the syntax carefully. The public key should not include spaces, line breaks, extra quotation marks, invalid characters, or copied labels such as “BEGIN PUBLIC KEY.” Many authentication failure issues are caused by a malformed DKIM record rather than a problem with the mail server itself.





    Key length matters. Modern email authentication best practice generally favors 2048-bit DKIM keys when supported. Some older DNS host interfaces historically had trouble with long TXT values, but reputable DNS management platforms such as Cloudflare, GoDaddy, Namecheap, and enterprise providers typically support split strings within a single DNS TXT record. The final resolved value must appear as one continuous DKIM record to the querying resolver.

    A weak or outdated public key can affect email security and domain reputation. Short keys are less resilient, and some mailbox providers may treat weak DomainKeys Identified Mail implementations as lower trust signals. For organizations using Digicert-managed services, enterprise security tools, or platforms such as Valimail, Agari, dmarcian, EasyDMARC, and DMARC Analyzer, key strength and proper key rotation should be part of a broader email policy.

    When validating the public key, check for these common issues:

    • The p= tag is empty, which can indicate a revoked DKIM record.

    • The public key is truncated because of DNS TXT record length limits.

    • The public key was pasted into the wrong selector record.

    • The DKIM selector in the email header points to an old public key.

    • The private key used by the sending system does not match the published public key.

    • The DNS record includes multiple conflicting DKIM values for the same selector.
