How To Check DKIM Records And Identify
Authentication Failures


Email authentication is essential for protecting business communications, preventing spoofing, and improving email deliverability. One of the most important technologies supporting this process is DomainKeys Identified Mail (DKIM), which uses cryptographic signatures to help receiving mail servers verify that an email was authorized by the sending domain and that signed portions of the message have not been altered.

However, incorrect DNS records, missing selectors, expired keys, and configuration mistakes can cause DKIM authentication failures. Knowing how to check DKIM records and troubleshoot these problems helps businesses maintain reliable email delivery and strengthen their security. Whether you use Microsoft 365, Google Workspace, or a third-party email service, regular DKIM checks are an important part of email administration.


What Is a DKIM Record and Why Does It Matter?


A DKIM record is a DNS TXT record that publishes the public key receiving mail servers need to verify an email's digital signature. The sending mail server uses a corresponding private key to sign outgoing messages.

When an email arrives, the recipient's mail server retrieves the public key from DNS and checks the signature. A successful verification indicates that the signature is valid and the signed message content has not changed in a way that invalidates it.

DKIM works alongside Sender Policy Framework (SPF) and Domain-based Message Authentication, Reporting, and Conformance (DMARC). Together, these protocols help receiving servers evaluate whether messages are legitimate and aligned with the domain visible to recipients.





How to Check DKIM Records Step by Step


1. Identify Your DKIM Selector

A selector identifies which DKIM public key should be used to verify a message. It forms part of the DNS lookup address, along with your domain.

You can often find the selector in an email's original headers by locating the DKIM-Signature field and checking the s= value. The d= value identifies the signing domain.

For example, if the selector is selector1 and the signing domain is example.com, the DNS record is typically located at:

selector1._domainkey.example.com

Your email provider's configuration instructions can help you identify the correct selector and expected DNS record.


2. Use a DKIM Lookup Tool

A DKIM record lookup tool can query DNS and show whether the expected TXT record exists and contains a public key. Enter the selector and domain in the appropriate fields, then review the results.

Check for missing records, incorrect hostnames, malformed key values, and unexpected DNS responses. Tools such as MXToolbox and EasyDMARC offer email authentication diagnostics that can help administrators investigate configuration problems.

Remember that a lookup tool checks the published DNS information; it does not necessarily confirm that every outgoing email is being signed correctly.


3. Verify the Record Using Command-Line Tools

Administrators can also inspect DKIM records directly using DNS utilities. For example, run this command in a terminal:

dig TXT selector1._domainkey.example.com

Alternatively, use nslookup:

nslookup -type=TXT selector1._domainkey.example.com

Replace the example selector and domain with your actual values. Review the returned TXT record to confirm that the public key is present and the DNS name matches your provider's instructions. Delve into this website for extra details.





Common DKIM Authentication Failures


Missing or Incorrect DNS Records

A missing record or an incorrectly configured hostname can prevent receiving servers from retrieving the public key. This often happens after domain migrations, DNS changes, or email provider updates.

Solution: Compare your published record with your provider's current configuration instructions. Correct the hostname or TXT value, then allow time for DNS changes to propagate.


Invalid Signatures or Key Mismatches

A DKIM failure can occur when the sending server signs messages with a private key that does not correspond to the public key published in DNS. Incorrect message handling or signature-generation settings can also invalidate verification.

Solution: Confirm that the active private key matches the published public key. Check the sending platform's DKIM configuration and generate or rotate keys if necessary.


Selector and DNS Propagation Problems

Some providers use multiple selectors during key rotation. If an email references a selector whose record has been removed prematurely, verification may fail. DNS caching can also delay the visibility of recently updated records.

Solution: Verify the selector in the message header, check its DNS record, and retain old keys for an appropriate transition period when required.
